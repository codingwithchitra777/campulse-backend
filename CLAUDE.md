# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`cambopulse-api` (local dir `campulse-backend`; GitHub `chitrasem001/cambopulse-api`) is the **FastAPI (Python 3.12) backend** for CamboPulse — a Cambodia-focused trading journal / portfolio tracker. It serves the `cambopulse-web` Angular app (sibling repo, has its own CLAUDE.md) **and** hosts the Telegram bot as a webhook. It's one of three CamboPulse repos that share a single database:

- `cambopulse-web` — Angular frontend (talks to this API).
- `cambopulse-api` — this service (REST API + Telegram webhook + background jobs).
- `campulse-bot` — the **retired** standalone polling bot; its features now live here as `app/services/telegram_bot.py`. Don't add features there.

> **Heads-up:** `README.md` describes an aspirational "Spring Boot / Java 21" stack and a Lowest-Price-First roadmap. That's marketing, not the code. The real stack is **FastAPI + psycopg2 + raw SQL** (see `pyproject.toml`).

## Commands

Always use the project venv's Python — the base interpreter is missing deps (e.g. `logfire`), which fails imports:

```bash
./.venv/Scripts/python.exe -m pytest -q -p no:warnings           # full suite
./.venv/Scripts/python.exe -m pytest tests/test_trades.py -q     # one file
./.venv/Scripts/python.exe -m pytest tests/test_trades.py::test_buy_trade_is_persisted   # one test
./.venv/Scripts/python.exe -m py_compile app/services/foo.py     # quick syntax check before a test run
./.venv/Scripts/python.exe -m uvicorn app.main:app --port 8001   # run locally (e.g. for web live-verify)
```

There is no lint step configured.

## Critical gotchas (read before running anything)

1. **Tests run against the PRODUCTION Neon Postgres.** There is no separate test DB — `get_db()` uses `settings.database_url` for everything, and `init_db()` runs on the first connection. So `pytest` (and even importing `app.main`) **connects to and migrates prod**. Consequences:
   - Tests that don't clean up leave `pytest_*` users behind. After a run, delete them by **exact enumerated id** — never a broad `LIKE`/pattern delete:
     ```python
     cur.execute("SELECT user_id FROM users WHERE user_id LIKE 'pytest_%'")
     ids = [r[0] for r in cur.fetchall()]
     cur.execute("DELETE FROM users WHERE user_id = ANY(%s)", (ids,))   # enumerate first, then delete exact ids
     ```
   - Use disposable ids and delete-by-exact-id in fixtures for new tests (see `tests/test_watchlist.py`, `test_gold.py`).
2. **The deployed backend auto-deploys on push to `main`** via GitHub Actions (`.github/workflows/deploy.yml` → `uv run fastapi deploy`), served at `https://api.cambopulse.com` (custom domain over `cambopulse-api.fastapicloud.dev`). No manual redeploy step needed — but the CI step needs two repo secrets that must refer to the **same** FastAPI Cloud app or it fails with a misleading "token is not valid" error: `FASTAPI_CLOUD_TOKEN` and `FASTAPI_CLOUD_APP_ID`. If a deploy fails with an invalid-token error, regenerate: `.venv\Scripts\python.exe -m fastapi_cli cloud apps list` (get the real app id — the local `.fastapicloud/cloud.json` can go stale after account migrations, don't trust it) → `... cloud tokens create --app-id <id> --name github-actions-ci --output-file <path>` → update both `FASTAPI_CLOUD_TOKEN` (from the file) and `FASTAPI_CLOUD_APP_ID` (the same `<id>`) as repo secrets, e.g. via `gh secret set`. (On Windows, `fastapi_cli` needs `$env:PYTHONIOENCODING="utf-8"` set first or it crashes on an emoji in its own output.) The workflow also pings an internal `deploy-notify` webhook after deploy, gated by a `DEPLOY_NOTIFY_SECRET` secret — that step is non-critical and failing there doesn't mean the deploy itself failed.
3. **Schema migrations live in `init_db()`** (`app/db/database.py`) as idempotent `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` / guarded `ALTER … TYPE`. They apply to prod the moment any code (including a test run) connects. Add new tables/columns there, keeping them idempotent.

## Architecture

Layered, no ORM — raw SQL via `psycopg2`:

```
app/api/v1/endpoints/*  →  app/services/*  →  app/repositories/*  →  app/db/database.py (pool + get_db + init_db)
```

- **DB access**: `get_db()` is a context manager that commits on success / rolls back on exception, backed by a `ThreadedConnectionPool`. Repositories run SQL with snake_case columns and return dicts with **camelCase** keys (except `chat_id`, `market`, `currency`, `note`, `tags`). When you add a column, thread it through the repo's SELECT lists + returned dicts (there are several per table).
- **Auth**: JWT. `app/api/deps.py` `get_current_user` / `require_admin` decode the bearer token; endpoints depend on them. Google / Telegram (login widget, Mini App `initData`) / demo logins all mint a JWT in `endpoints/auth.py`.
- **Account identity**: Google is the canonical account; a Telegram id is an alias linked via a one-time code. `services/identity.resolve_primary()` maps alias→primary at login and bot-write time (`user_links` / `link_codes`), so a linked Telegram user reads/writes the same portfolio.
- **Multi-market money** (the load-bearing design):
  - `services/markets.py` defines markets `CSX | US | GOLD_KH`, their currency (`KHR | USD`), and `quantize_money(value, currency)` (KHR=0dp, USD=2dp).
  - Money is **`Decimal` end-to-end**, stored as `NUMERIC` (never float); FastAPI serializes `Decimal` to a JSON number.
  - `services/price_providers.PriceRouter` routes `get_latest_price(market, symbol)` to `CSXProvider` (CSX feed), `FinnhubProvider` (US, needs `FINNHUB_API_KEY`; also company-news + symbol search), or `ManualProvider` (local gold `XAU-KH`). `ManualProvider` reads the **latest `price_history` row** — the single write path shared by `/setgold`, the gold-OCR photo flow, and `/api/admin/gold-history` (`pages/admin/admin-gold` on the web). There used to be a second, separate `manual_prices` table + `PUT /api/admin/manual-price` endpoint that a different (now-deleted) admin widget wrote to — it silently desynced from the real board since none of the other gold-setting flows touched it, so portfolio valuation could show a stale price while the Markets/gold-detail views showed the current one. Don't reintroduce a second gold price source; if you need to change how gold is valued, change `ManualProvider`/`price_history`, not a parallel table.
  - Matching (`services/best_profit_matcher.BestProfitMatcherService.match_sell` / `simulate_sell`) is **cheapest-lot-first** (best-profit) — **not** LIFO, despite the historical naming that was purged; don't reintroduce "LIFO" in code or copy. It's **scoped by market** so a US `ABC` never matches a CSX `ABC`. `services/trade_service.record_trade()` is the single write path shared by `POST /trades` and the Telegram bot.
- **Redis is a cache, never the system of record.** `services/redis_service.py` holds the live CSX price blob (`csx:latest_prices`), 60-day sparkline hashes, and the poll lock — but every one of those is also in Postgres (`price_history`, dual-written by `snapshot_prices`). Rules to preserve:
  - **Never read Redis directly from an endpoint.** Go through `PricingService`, which degrades: **Redis → last-good in-process fetch (`_memory_prices`) → Postgres (`get_latest_snapshot_all` / `get_sparklines`) → static `FALLBACK_PRICES`**. DB-sourced rows carry `stale: True` (+ `asOf`) and `change: 0`, since history has no intraday change. The DB read is TTL-cached (`DB_FALLBACK_TTL_SECONDS`) so an outage can't stampede Postgres.
  - `RedisService` methods **never raise** — they return `[]`/`{}`/`False` and trip a **circuit breaker** (`CIRCUIT_OPEN_SECONDS`), logging once per outage transition rather than once per call. `svc.available` reports the state.
  - The price-poll loop runs **without** the Redis lock when Redis is unavailable (`acquire_lock(...) or not redis_service.available`) — otherwise a Redis outage would silently stop price refreshes *and* daily snapshots.
  - `REDIS_URL` is **env-only (no default)**; unset simply means "Postgres only". Never commit credentials there.
  - Guarded by `tests/test_price_fallback.py` — keep it passing.
- **Background daemon threads** (single-instance assumption; all **dormant unless `TELEGRAM_WEBHOOK_SECRET` is set**, so they're no-ops in tests/local): `PricingService` price-refresh + daily snapshot loop; `reminder_scheduler` (08:00/14:00 Asia/Phnom_Penh session reminders); `alert_service` (polls `price_alerts`, messages the user's linked Telegram on a cross); `corporate_action_service` (applies bonus/split on the ex-date); `loan_service` (reminds about loans due within 3 days, once a day via `loans.last_reminded_date`). Started from `main.py`'s lifespan.
- **Loan ledger** (`services/loan_service.py`, `repositories/loan.py`): a personal debt tracker — money `lent` to / `borrowed` from a named person — kept **entirely separate from trading** (never touches P/L, holdings, or the equity curve). `loans` + `loan_repayments`; `outstanding = principal − Σ repayments` is always computed, `status` (open/partial/settled) is a derived cache recomputed on any repayment change. Currencies are never blended (KHR and USD stay on separate summary rows). Recording a repayment sends the user a **forwardable Telegram receipt** (best-effort, silent without a linked chat) so they can pass it to the other party.
- **Telegram webhook URL**: registered with Telegram via `setWebhook`, independent of FastAPI Cloud's own routing — if the app's domain ever changes, the Telegram side does **not** follow automatically. Check where Telegram is actually sending updates with `GET https://api.telegram.org/bot<TOKEN>/getWebhookInfo`, and repoint it with `POST .../setWebhook` (`{"url": "https://api.cambopulse.com/api/telegram/webhook", "secret_token": "<TELEGRAM_WEBHOOK_SECRET>"}`) if it's stale. A stale webhook is a silent failure mode: the bot still replies (from whatever old deployment it's still pointed at), so commands just look broken/outdated rather than erroring.
- **Telegram**: `endpoints/telegram.py` validates the `X-Telegram-Bot-Api-Secret-Token` header, then `TelegramBotService` dispatches slash commands and replies via `services/telegram_client.py` (module-level `send_message` / `send_photo` / `download_file`). Chart images are rendered with matplotlib in `app/utils/chart_renderer.py`. **A photo message** from an **admin** (canonical account role `admin`, resolved via `link_repo.get_primary`) is treated as the daily **gold price board**: the webhook offloads it to a thread → `handle_gold_image` downloads it → `services/gold_ocr.parse_gold_board` (RapidOCR/ONNX, no PyTorch; lazy import so the app still boots without it) reads the numbers → it saves via the **same path as the manual admin form** (`upsert_snapshot("XAU-KH", today, mid, market="GOLD_KH", bid_price=…, ask_price=…)`). App convention: **bid = the higher លក់ចេញ/sell-out, ask = the lower ទិញចូល/buy-in**; default row 1 (bar), overridable by sending a caption `1`–`4`. Standalone/tunable version lives in the sibling `gold-ocr/` folder. Guarded by `tests/test_gold_bot.py`. Admins also have text-command shortcuts that hit the same write paths: `/setgold <bid> <ask> [YYYY-MM-DD]` (same `upsert_snapshot` call as the photo flow; date defaults to today, and — like the photo flow and the web admin form — the same date can be set repeatedly in one day, each call overwriting that date's row rather than erroring) and `/setrate <bid> <ask> [BASE TARGET] [YYYY-MM-DD]` (defaults `USD KHR`/today, writes via `ExchangeRateRepository.add_rate` which upserts on `(base, target, date)` — the date token can appear anywhere after bid/ask, detected by whichever argument parses as `YYYY-MM-DD`).
- **Voice → Khmer text**: a **voice note or audio file** from anyone is offloaded to a thread → `handle_voice` downloads it → `services/transcriber.transcribe` (Whisper `chitra168/whisper-small-khmer-mini`, OGG/Opus decoded via `soundfile`, resampled to 16 kHz, split into 10s chunks since the model was trained on ≤10s clips) → replies to the voice message with the text. torch/transformers/soundfile/scipy are **main dependencies** (torch pinned to the CPU-only PyTorch index via `[tool.uv.sources]` — the default Linux wheel drags in GBs of CUDA); still lazily imported, so if they're missing the bot says "not available" instead of crashing. The model downloads from Hugging Face and loads once on first use, in **bfloat16** (~950 MB peak) — fp32 peaked ~1.5 GB and got the FastAPI Cloud container OOM-killed mid-transcription (shows up as a silent restart, no traceback). Transcriptions are serialized by `_run_lock` for the same reason. The model repo's `generation_config.eos_token_id` is a list, which crashes transformers 5's timestamp processor — `_load()` normalizes it; keep that. Guarded by `tests/test_voice_bot.py`.
- **Grid trading plans** (`endpoints/grid.py`, `repositories/grid.py`): `GET/PUT/DELETE /api/grid` store a user's ladder plan(s) as JSON (`GridPlanBody`, keyed by client-chosen `id` — a user can hold several grids, e.g. one per ticker). This is bookkeeping only, not execution: recording an actual fill is a normal `POST /trades/confirm` from the client.
- **Coach** — two coaches over one snapshot. `services/rule_coach.py` is the **free default**: deterministic sentences built from the snapshot, no key, no credit, no network, so `GET /api/ai/insights` can never fail on billing. `services/ai_coach.py` is the **optional paid pass** (`POST /api/ai/insights`) for cross-signal reading the templates can't do. Both consume the same `build_snapshot()` output — keep it that way so they can't drift, and hold both to the same descriptive-never-advisory rule (`test_rule_coach.py::test_never_gives_advice`).
- **AI Coach** (`services/ai_coach.py`): `AnalyticsService.compute()` → `build_snapshot()` → Claude → cached in `ai_insights` keyed by `snapshot_hash`. Two rules the code (not the prompt) enforces: **descriptive, never advisory** (real money, we're not licensed advisers — `DISCLAIMER` is appended server-side), and **no PII off-box** — `build_snapshot()` is an *allow-list*, never a dict spread, so a new `users`/`trades` column can't leak. `test_ai_coach.py::test_snapshot_leaks_no_pii` guards this; keep it passing. Degrades to `enabled: false` with no `ANTHROPIC_API_KEY` rather than erroring. Regenerates only when the snapshot hash changes, and at most once per user per day.
- **Config**: `app/core/config.py` is a frozen `Settings` dataclass read from env **at import time** (`DATABASE_URL`, `JWT_SECRET`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_BOT_USERNAME`, `FINNHUB_API_KEY`, `GOOGLE_CLIENT_ID`, `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`).

Feature endpoints beyond core trading: `analytics` (win rate, hold time, per-currency + per-journal-tag stats), `watchlist`, `alerts`, `market` (news/search/quote), `ai` (coach insights + an admin-only `GET /api/ai/health` that makes one real ~$0.0003 call to prove the key works on the deployed box), `admin` (users, stats, manual gold-price board). Keep response shapes in sync with `campulse-web`'s `src/app/models.ts`.

## Verifying a change

Because tests hit prod and the bot threads are gated off locally, verify with `pytest` (behavior-preserving refactors must keep the existing suite green) plus, for provider/webhook paths, either monkeypatched HTTP or a live check against the deployed base URL. Add tests that create rows under disposable ids and clean up by exact id on teardown.
